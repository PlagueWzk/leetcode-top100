# 2026-10-02：有界线程池的任务去向

预计 5–7 分钟。最低 Java 版本：Java 8。前两天的 `CompletableFuture` 代码题仍待作答；今天只练支撑显式 `Executor` 的线程池容量判断，不新增编码任务。

对常见的 `ThreadPoolExecutor` 配置，提交任务时先使用未达到核心数的工作线程；核心线程都忙后，任务进入队列；队列满后，线程数才继续增长到最大值；仍无法接收时执行拒绝策略。这里讨论的是初始线程数为 0、无预启动、任务持续阻塞的情形。

## 题 1：原理解释

线程池配置为 `corePoolSize=1`、`maximumPoolSize=2`、容量为 1 的 `ArrayBlockingQueue`、`AbortPolicy`。连续提交 4 个任务，每个任务都一直阻塞，提交期间没有任务完成。请按提交顺序写出第 1–4 个任务分别是“立即执行、排队、创建新线程执行、被拒绝”中的哪一种，并说明原因。

> 回答：
> 1. 立即执行
> 2. 排队
> 3. 创建新线程执行
> 4. 同上
> 若还有第五个任务则直接拒绝

## 题 2：代码判断

```java
new ThreadPoolExecutor(
        2, 8, 0L, TimeUnit.MILLISECONDS,
        new LinkedBlockingQueue<Runnable>());
```

有人认为：“并发任务多时，这个池会自然扩到 8 个线程，从而缩短等待。”在任务生产速度持续高于处理速度、且不耗尽内存的前提下，这个判断通常成立吗？为什么？

> 回答:
> 这个线程池的配置:核心/常驻线程2个,最大8线程,辅助线程无任务时存活0ms,排队队列为阻塞链表队列.
> 当任务来到两个及以上时,后续所有任务都会存入LinkedBlockingQueue,该列表无上限(未设置),因此不会触发创建新线程,不会扩到8线程,始终只有两个线程工作

## 题 3：业务改写

一个后端接口用题 2 的池执行耗时的外部查询。现在要求“等待任务数量有明确上限；满载时立即让调用方知道任务未被接收”。请**用文字**说明你会改哪两处线程池配置，以及提交任务的代码需要处理哪一种结果或异常；不用写 Java 代码。限定不丢弃已接收的任务，不让请求线程代替工作线程执行查询。

示例答题格式：`1. ... 2. ... 3. 队列改为...；拒绝策略...；提交处...`。题目只要求判断和改造思路，暂不提供参考答案。

> 回答:
> 队列改为ArrayBlockingQueue(上限),拒绝策略使用AbortPolicy.代码捕获失败策略处理告知用户未被接收
