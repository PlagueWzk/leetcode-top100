# JVM：一天建立面试框架

目标是能解释常见现象并说出排查顺序，不是一天学会所有 GC 参数。学习时区分 JDK 8 实习项目和个人练习可能使用的较新 JDK；命令与默认收集器要按目标版本确认。

## 今天的四段学习

1. **内存区域**：堆放对象实例；线程栈放方法调用帧；元空间存类元数据。不要把“方法区”“元空间”“永久代”无条件当同义词。
2. **对象回收**：从 GC Roots 出发判断可达性。局部变量出了作用域，不表示立刻回收；只要仍有可达引用，对象可能继续存活。
3. **GC 指标**：看分配速率、回收后存活量、暂停时间、吞吐量与 Full GC 频率。停顿目标与吞吐量存在权衡，不能只靠调大堆或盲改参数。[Oracle GC 调优指南](https://docs.oracle.com/en/java/javase/21/gctuning/)
4. **排障**：先确认变慢是 CPU、锁、I/O 还是 GC；若与 GC 同时变化，再看日志和堆使用趋势。必要时取线程栈、类直方图和堆转储，分析保留对象的引用链。堆转储可能有明显开销并包含敏感数据，实际环境需按操作规范处理。[Oracle jcmd 诊断说明](https://docs.oracle.com/en/java/javase/21/troubleshoot/diagnostic-tools.html)

## “GC 越来越频繁”口述模板

> 我先比较请求量、延迟、CPU 和 GC 指标的时间线，确认是分配速率升高还是回收后存活量持续上涨。如果后者持续增加，再看大对象/集合、缓存、ThreadLocal 或类加载器等保留路径；用堆直方图或堆转储验证。若对象量稳定但停顿仍长，再检查 GC 日志与收集器/堆配置，并做改动前后对比。

这是一套诊断顺序，不等于已经在实习项目做过 JVM 调优。G1 是较新 HotSpot 服务端场景的重要收集器，但具体进程的收集器必须看启动参数或运行时配置。[Oracle G1 文档](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-g1-garbage-collector1.html)

## 常见追问

- `OutOfMemoryError: Java heap space`、`Metaspace`、`StackOverflowError` 的排查起点有什么不同？
- 内存泄漏和内存溢出是什么关系？哪些“仍可达但不再需要”的对象会造成泄漏？
- 为什么“CPU 高、接口慢”不一定是 GC 问题？
- `volatile` 与 Java 内存模型属于并发正确性知识，与 JVM 堆结构不是同一个问题。

一天内只需画出内存区域图、讲出一次对象存活/回收过程，再按上面的模板口述一次诊断。

## 把三个相似现象分开

“接口慢且 CPU 高”先看线程栈：大量线程在业务计算、锁竞争或 GC 线程活动，方向不同；“堆占用高”要区分 GC 前瞬时占用与每次 GC 后仍持续上升；“进程内存高”也可能包含堆外内存，不能只看 Java 堆。若回收后的存活量稳定而分配速率很高，优先查大量短命对象与请求流量；若回收后存活量持续上升，沿 GC Roots 找长时间保留引用。一次堆快照只说明取样时的可达关系，需要结合时间趋势。

练习记录模板：**现象时间段 → 请求量/延迟/CPU/GC 曲线 → 首个假设 → 用哪项证据证伪或支持 → 下一步**。可以在自己的小程序里持续向静态集合加入对象，再停止加入，观察两段的回收后存活量；练习环境用 `jcmd <pid> GC.heap_info`、`jcmd <pid> Thread.print` 等命令前先运行 `jcmd -l` 找自己的进程。命令可用性依 JDK 与目标进程权限而定，遇到生产系统遵守操作规范。无需为此另建一个无关的面试题类。
