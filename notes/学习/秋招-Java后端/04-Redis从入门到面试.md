# Redis：从少量接触到能应对后端面试

先掌握用途：Redis 是内存数据存储，Java 后端常用作缓存、计数、限流等。它并不自动代替关系数据库的事务和唯一约束。下面按“一个商品详情接口”学习。

## 最基础的读缓存流程

读 `product:123`：先查 Redis；命中则返回；未命中则查数据库，把结果写入 Redis 并设置 TTL，再返回。写数据库后删除对应缓存，让下一次读取重建。这叫 cache-aside。[Redis 官方 cache-aside 指南](https://redis.io/docs/latest/develop/use-cases/cache-aside/)

回答“为什么要 TTL”：它限制陈旧值的存活时间，也让异常情况下的缓存最终有恢复机会；TTL **不保证强一致**。写库成功、删缓存失败，或读写请求交错，仍可能短暂读到旧值。数据正确性要求越高，越要明确允许的陈旧时间和补偿手段。

## 必会命令与结构

| 类型 | 最小需要掌握的场景 |
|---|---|
| String | 缓存一个序列化对象、计数器；`GET`、`SET`、`INCR` |
| Hash | 一个对象的多个字段；`HGET`、`HSET` |
| Set | 去重、成员判断；`SADD`、`SISMEMBER` |
| Sorted Set | 按分数排序；`ZADD`、`ZRANGE` |
| List / Stream | 认识队列与消息流语义；校招阶段先不必背全部命令 |

用 `SET key value EX seconds NX` 可以把“只在不存在时写入”和过期时间放在同一条命令中。不要先 `SETNX` 再 `EXPIRE`，两条操作之间进程崩溃可能留下没有 TTL 的键。[Redis SET 文档](https://redis.io/docs/latest/commands/set/)

## 四类缓存故障

| 问题 | 发生了什么 | 入门应对思路 |
|---|---|---|
| 穿透 | 查询不存在的键，每次都打到数据库 | 缓存短 TTL 的空结果、布隆过滤器；先验证是否真有大量无效键 |
| 击穿 | 热点键过期，大量请求同时回源 | 热点续期、请求合并/单飞、互斥重建，注意锁失败后的返回策略 |
| 雪崩 | 大量键同时过期或 Redis 不可用 | TTL 加随机抖动、限流降级、多副本与容量规划 |
| 热键 | 单个键访问过于集中 | 指标识别、局部缓存/分片等，注意一致性代价 |

先说现象与证据，再选方案；不要四个词一出现就把所有治理措施堆上去。[Redis cache-aside 指南](https://redis.io/docs/latest/develop/use-cases/cache-aside/)

## 分布式锁的边界

`SET key token NX PX ttl` 获得有过期时间的锁；释放时只删除仍归自己 `token` 所有的锁，通常通过原子脚本完成。锁可能到期而任务仍在执行，因此它不自动保证关键业务写入唯一。库存、转账等仍应由数据库条件更新、唯一约束或业务幂等兜底。[Redis 分布式锁文档](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

## 把缓存流程拆成可观察的步骤

读商品：查缓存；有值就返回；未命中查主存储；查到后写入带 TTL 的缓存；返回。更新商品：先更新主存储，成功后删除缓存。这个顺序的主要竞态是：读请求先发现缓存未命中并读到旧值；写请求更新数据库、删缓存；先前的读请求最后又把旧值写回缓存。**删除成功也不能证明此后绝不出现旧值**；TTL 只限制旧值可能存活的时间，且依赖写入时确实设置 TTL。可按业务容忍的陈旧窗口决定是否需要版本号、延迟二次删除或更强方案，不要未经测量就叠加所有机制。参见 [Redis cache-aside 说明](https://redis.io/docs/latest/develop/use-cases/cache-aside/)。

不存在的商品和缓存未命中要分开表示。当前 Java 骨架的 `Optional.empty()` 只表示“缓存没有条目”，所以基础题**不缓存空结果**；做穿透扩展时先改缓存接口，使它能表达“查过但不存在”，再给空值较短 TTL。Redis 不可用时是否回源取决于数据库承载量和业务可用性要求，不能默认为无限回源。
