## 建议重点准备的三个故事

### 1. 资金计划：一次失败响应不等于整条业务回滚

**背景**：接口需要调用标准服务创建计划或调整单，再走检查、计算及审批流程。调用链可能部分成功。

**个人贡献**：从提交记录看，参与新增/调整 REST 服务、参数校验、RPC 返回解析、错误反馈和审批回调处理。面试时可以画出 `请求 → 生成 → 检查/计算 → 提交审批 → 核对单据/流程`。

**困难与判断**：曾出现“计划已新增，提交审批失败”的响应；已有计划不能无脑重试 `/add`。另一次开发库核对表明，新调整单实际上完成生成、计算和提交，后续同类请求才被运行中的流程拦截。正确做法是按单号和流程实例核对各阶段，再决定是否重试或恢复。

**验证边界**：单次开发库结果只证明那次调用与那套环境的状态。不能说“资金计划所有场景已生产稳定运行”或“接口保证 exactly once”。

对话依据：Codex 任务 `01a0801e-93d2-77a2-b788-20c7826a6719`、`01a0c75d-54b3-7800-95a8-1e74cc76d394`。后者曾核对一张新调整单：调整记录 6 条、汇总 1 条、明细 2 条，并发现业务单据删除后工作流仍残留的独立问题。这些是**特定测试数据的数量**，不可作为系统规模或普遍成功率。

### 2. 信用证：统一入口与标准 RPC 之间的契约适配

**背景**：外部调用方希望通过少量稳定入口推送不同信用证场景，平台标准服务却有不同的字段与参数包装要求。

**个人贡献**：提交记录显示参与统一推送 API、场景枚举、字段转换、校验和日志处理。

**难点**：标准接口既要求准确的外层参数名和嵌套层数，也要求操作类型在正确位置；仅凭 HTTP 成功响应不能证明业务落库。

**可举的验证例**：一次国内收证测试中，对话记录显示标准 RPC 返回成功，随后开发库 `TMXYZ` 中找到与返回 ID 一致的 1 条业务记录，按业务编号和来源内码分别核对也各为 1 条。对话任务：`01a0c19f-b051-7333-98f2-05bee75d96ac`。这是**一个场景的一次开发环境验证**；其余场景、更新链路和后续代码版本需分别验证。

### 3. 银行定义：全量同步与字段语义

**背景**：自动任务从平台银行定义取数，下发给外部系统，停用银行也要传递状态，不能因为“停用”就直接漏掉。

**个人贡献**：提交记录显示新增自动任务，并持续调整 SQL、启用状态和引用字段的编号/名称映射。

**可量化且诚实的说法**：一次开发库核对中，源表有启用 **158,083** 条、未启用 **8,625** 条，合计 **166,708** 条；SQL 查询覆盖两类数据。这个数字证明的是**当时开发库查询范围**，不证明自动任务已经实际下发 166,708 条，更不证明外部系统全部接收。对话任务：`01a09efa-f151-7150-8351-e7b7165ff9a8`。

## 面试追问与回答边界

| 追问 | 回答主线 |
|---|---|
| 为什么不直接重试？ | 请求可能已经生成单据或启动流程；先用业务键、单号、流程状态判定，再处理重复调用 |
| 怎么证明接口成功？ | 看接口返回、标准 RPC 返回、业务表记录、工作流/受影响数据；每项回答对应哪次测试 |
| 你做了多少？ | 44 个个人非合并提交、23 个涉及文件是可复核的版本记录；具体职责举源码与测试例子 |
| 用了 MySQL、Redis、MQ 吗？ | 这个实习模块以 Oracle/JPA/平台 RPC 为主；不要为迎合岗位把学习过的组件说成项目已用 |
| 是否上线？ | 按对应功能实际部署记录回答。没有证据时说“源码/构建/开发库联调达到的阶段”，不推断生产状态 |

## 面试前自查

- 准备一张自己画的调用链图，不展示客户账号、凭据、真实业务报文。
- 每个故事准备“需求、自己的决策、替代方案、错误案例、验证结果”各一句。
- 对正在变动的功能，面试前重看最新源码与测试记录；不要照搬旧对话结论。
