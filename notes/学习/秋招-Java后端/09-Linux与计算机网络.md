# Linux 与网络：围绕接口故障复习

目标不是背 Linux 命令大全，而是能回答“一个 Java 接口超时，我从哪里开始排查”。

## 从请求链路看问题

`客户端 → DNS → TCP 连接 → TLS/网关 → Java 服务 → 数据库/下游 RPC → 响应`

先记录请求 ID、时间、目标地址、HTTP 状态和耗时，再定位哪一段变慢。一次 `HTTP 302` 可能是认证跳转；`401` 是未认证；`403` 是已识别身份但拒绝访问；`5xx` 还要继续看网关与上游服务日志。不要单凭状态码断定根因。

## Linux 最小命令集

| 命令 | 用来回答什么 |
|---|---|
| `pwd`、`ls`、`cat`、`less` | 当前目录、文件和配置在哪里 |
| `ps`、`top` | 进程是否存在、CPU/内存大致情况 |
| `ss -lntp` | 端口是否监听、由哪个进程监听 |
| `curl -v` | 请求是否到目标，HTTP/跳转/TLS 信息是什么 |
| `grep`、`tail`、`journalctl` | 在指定时间范围和请求 ID 下找日志 |
| `df -h`、`free -h` | 磁盘与内存是否紧张 |

正式环境使用命令时，先遵循权限和变更规范。查看配置或日志注意避免输出令牌、账号和完整业务报文。

## 网络面试重点

- TCP 建连与连接超时、读超时：连接不上和连接后等响应过久是不同问题。
- HTTP 方法、状态码、幂等语义：`POST` 不会因为名字叫“新增”就自动防重复。
- DNS、反向代理、负载均衡：确认解析与路由实际到了哪个服务实例。
- 连接池：数据库或 HTTP 连接池耗尽会让请求排队，表现为接口慢，未必是下游单次调用慢。

结合实习项目可以讲一次 RPC 参数或业务校验问题如何通过请求 ID、服务日志与开发库记录逐层定位；不要把网络、认证、业务失败混为一个错误。

## 自测

- `curl` 返回 302，后续跳到登录页；为什么不能称为业务接口调用成功？
- 服务监听端口正常，但请求偶发超时，你会看什么指标？
- 连接超时与读取超时分别发生在调用链的什么阶段？

## 一次超时的逐层记录法

假设客户端报“接口超时”，先固定请求 ID、客户端发起时间和最终错误，再按层找证据。DNS 解析失败时通常还没建立 TCP；连接超时说明 TCP 连接阶段没完成；连接已建立但读取超时说明请求后没有在期限内收到所需响应；拿到 302 登录页则是认证/路由线索，不能称为业务成功。服务端日志显示请求进入但数据库连接池一直等待时，问题也不等于“数据库单条 SQL 慢”。

练习：针对自己的本地服务分别制造“端口未监听”“服务收到请求但故意睡眠”“返回 302 登录页”三种现象。每次记录 `curl -v` 中连接、响应与耗时线索，服务日志中是否出现同一请求 ID，以及你下一步会查的指标。Linux 命令在 Linux 环境练；当前 Windows PowerShell 可以先做 HTTP 现象实验，不要把两种 shell 的命令和默认输出混用。无需为了本篇另写一个 Java 算法题。
