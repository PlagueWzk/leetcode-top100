# 消息队列：先学一套可靠的收发链路

优先选 RabbitMQ 或 Kafka 中**目标岗位更常出现的一种**动手实现；校招面试先把通用可靠性讲清，再补产品专有概念。两者都不是“发了就一定处理成功”。

## 什么时候用

- 异步：把不必阻塞主请求的任务交给消费者。
- 解耦：生产者不直接依赖每个下游服务。
- 削峰：缓冲突发流量，消费者按可承受速度处理。

代价是结果延后、状态追踪变复杂、消息重复或失败时需要恢复。重要且必须同步确认结果的操作，不能因为用了 MQ 就随意改成“先返回成功”。

## 一条消息经过哪些阶段

`业务写库 → 生产者发送 → Broker 接收/持久化 → 消费者收到 → 业务处理 → 确认/提交进度`

每一段都要问“这一步成功，但下一步失败怎么办”。以 RabbitMQ 为例，publisher confirm 证明 Broker 对发布作出确认；consumer acknowledgement 说明消费者确认了投递处理，这两种确认彼此独立，不能互相代替。[RabbitMQ 确认机制](https://www.rabbitmq.com/docs/confirms)

## 重复消费与幂等

消费者完成数据库写入后，在确认消息前崩溃，消息可能再次投递。应以稳定业务 ID 建立去重记录、唯一约束或条件更新，使重复处理得到可接受结果。不要只在进程内用 `Set` 记录“已处理”，重启或多实例后会失效。

面试说“至少一次投递”时要补一句：应用要容忍重复；不要轻易声称跨数据库与消息系统实现了全局 exactly once。

## 重试与死信

临时故障可延迟重试；永久性数据错误需要隔离、告警或死信处理，不能立即无限重试造成循环风暴。需要明确最大次数、退避、人工处理和补偿入口。RabbitMQ 文档讨论了重投递、确认及其可靠性边界。[RabbitMQ 可靠性指南](https://www.rabbitmq.com/docs/reliability)

## 一定要做的最小实验

1. 生产者发送带业务 ID 的消息，消费者写一条业务记录。
2. 在写库后、确认前故意使消费者退出，再启动，观察是否重复。
3. 加入去重约束，确认重复投递不会产生第二条业务记录。
4. 模拟 Broker 不可用与消费者长期失败，记录主业务怎样反馈和告警。

这一步做完，面试可说“在本地实验过可靠消费”；尚未用于实习项目就不要说“项目使用了 MQ”。

## 用两个故障窗口理解确认

生产者已发送但没有收到 Broker confirm：不能从“没收到确认”推断 Broker 一定没收；重发时要容忍重复。消费者已经写库但还没 ack 就崩溃：Broker 可再次投递；第二次消费必须识别同一业务事件。publisher confirm 与 consumer ack 管理的是两段不同链路，并不能替业务数据库做去重。[RabbitMQ 确认机制](https://www.rabbitmq.com/docs/confirms)

可靠消费的最小数据库设计是：`processed_message(message_id UNIQUE)` 与业务变更在**同一个本地事务**提交。事务失败则两者都回滚；事务成功后才 ack。重复投递时唯一约束阻止第二次业务变更，再确认该重复投递。若业务变更涉及外部系统，本地事务仍覆盖不了远端，需另设计幂等与补偿。
